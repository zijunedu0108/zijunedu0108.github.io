DBMS Normalization

1. What is Database Normalization?

Definition: Database normalization is the process of organizing data in a database to reduce data redundancy and prevent data anomalies.

Main objectives:

  • Reduce data redundancy
  • Prevent data inconsistency
  • Avoid insertion anomalies
  • Avoid update anomalies
  • Avoid deletion anomalies

Functional Dependency (FD)

A Functional Dependency means one attribute's value determines another attribute's value.

StudentID → StudentName

Meaning: knowing StudentID, you can determine StudentName. The symbol → stands for determines.

2. UNF — Unnormalised Form

UNF is a data structure that has not been normalized yet.

Characteristics:

  • May contain repeating groups.
  • May contain multiple values in one field.
  • Data is not properly organised.
Example — Student Course Registration (UNF)
StudentIDStudentNameCourses
S01AliBiology, Chemistry
S02MeiPhysics, Biology

The Courses field contains multiple course values. For S01, it stores both Biology and Chemistry. This is a Repeating Group.

Problem: Data is not normalized, making it difficult to query, update, and manage each course independently.

3. 1NF — First Normal Form

Definition: A table is in 1NF if all attributes contain atomic values and there are no repeating groups.

How it works:

  • Identify repeating groups.
  • Separate multiple values.
  • Ensure each cell contains only one value.
  • Identify a suitable primary key.
Example — 1NF (Student Course Registration)
StudentIDStudentNameCourse
S01AliBiology
S01AliChemistry
S02MeiPhysics
S02MeiBiology

Now every cell has a single value, so it satisfies 1NF. However, StudentName still repeats.

This leads us to 2NF.

4. Composite Primary Key

A Composite Primary Key consists of two or more attributes combined.

Example — Composite Key (StudentID, CourseID)
StudentIDCourseIDStudentNameCourseNameMarks
S01C01AliBiology85
S01C02AliChemistry90
S02C01MeiBiology78

Assume: a student can register for multiple courses; a course can have multiple students; Marks depends on both student and course.

(StudentID, CourseID) → Marks

StudentID and CourseID together uniquely determine Marks. So the Composite Primary Key is (StudentID, CourseID).

5. Full Functional Dependency

Definition: Full functional dependency occurs when a non-key attribute depends on the entire composite primary key, not just part of it.

Example:

(StudentID, CourseID) → Marks

Why? StudentID alone cannot determine Marks. CourseID alone cannot determine Marks. Both are needed. Therefore, Marks is fully functionally dependent.

Remember: Full = depends on the WHOLE composite key.

6. Partial Functional Dependency

Definition: Partial functional dependency occurs when a non-key attribute depends on only part of a composite primary key instead of the entire key.

Example:

StudentID → StudentName

Why? Knowing StudentID is enough to determine StudentName. We do not need CourseID. Thus StudentName depends on a part of the composite key.

Another example: CourseID → CourseName. CourseName depends only on CourseID.

How to eliminate? Split the table:

STUDENT TABLE

StudentID (PK)StudentName
S01Ali
S02Mei

COURSE TABLE

CourseID (PK)CourseName
C01Biology
C02Chemistry

REGISTRATION TABLE

StudentID (PK, FK)CourseID (PK, FK)Marks
S01C0185
S01C0290
S02C0178

Now StudentName and CourseName no longer depend on part of the composite key. This eliminates Partial Functional Dependency.

7. Transitive Functional Dependency

Definition: Transitive functional dependency occurs when a non-key attribute depends on another non-key attribute instead of depending directly on the primary key.
Example — Transitive FD (Department)
StudentID (PK)StudentNameDepartmentIDDepartmentName
S01AliD01Biology
S02MeiD02Chemistry
S03JohnD01Biology

We know: StudentID → DepartmentID and DepartmentID → DepartmentName, therefore StudentID → DepartmentName.

Here DepartmentName does not directly depend on StudentID; it is determined through DepartmentID. This is a Transitive Functional Dependency.

How to eliminate? Split the table:

STUDENT TABLE

StudentID (PK)StudentNameDepartmentID (FK)
S01AliD01
S02MeiD02
S03JohnD01

DEPARTMENT TABLE

DepartmentID (PK)DepartmentName
D01Biology
D02Chemistry

Now DepartmentName directly depends on DepartmentID, not indirectly through StudentID.

8. 2NF — Second Normal Form

Definition: A table is in 2NF if it is already in 1NF and has no partial functional dependency.

How it works:

  • Ensure the table is in 1NF.
  • Identify the composite primary key.
  • Identify partial functional dependencies.
  • Remove partial dependencies by separating the tables.

Key point: 2NF = 1NF + No Partial Functional Dependency.

Example — 2NF Result (from earlier split)
StudentID (PK)StudentName
S01Ali
S02Mei
CourseID (PK)CourseName
C01Biology
C02Chemistry
StudentID (PK, FK)CourseID (PK, FK)Marks
S01C0185
S01C0290
S02C0178
Note: If the primary key consists of a single attribute, there can be no partial dependency caused by a composite key.

9. 3NF — Third Normal Form

Definition: A table is in 3NF if it is already in 2NF and has no transitive functional dependency of non-key attributes on candidate keys.

How it works:

  • Ensure the table is in 2NF.
  • Identify transitive functional dependencies.
  • Separate attributes that depend on other non-key attributes.
  • Create new tables with appropriate primary and foreign keys.

Key point: 3NF = 2NF + No Transitive Functional Dependency.

Example — 3NF Result (Department split)
StudentID (PK)StudentNameDepartmentID (FK)
S01AliD01
S02MeiD02
S03JohnD01
DepartmentID (PK)DepartmentName
D01Biology
D02Chemistry

Now DepartmentName directly depends on DepartmentID, not indirectly through StudentID.

10. Summary: UNF → 1NF → 2NF → 3NF

Normal FormMain RequirementEliminates
UNFUnnormalisedRepeating groups not yet handled
1NFAtomic ValuesRepeating Groups
2NF1NF + No Partial FDPartial Dependency
3NF2NF + No Transitive FDTransitive Dependency

Exam memory tips:

  • 1NF: One cell = One value
  • 2NF: Whole Key Dependency — eliminate Partial FD
  • 3NF: Nothing but the Key — eliminate Transitive FD
Special note: Both 2NF and 3NF require considering Candidate Keys and Functional Dependencies — not just checking for duplicate data.

My suggestion: practice a full normalization exercise from UNF step by step to 3NF, so you truly master how to decompose tables in the exam.

1. Apakah Penormalan Pangkalan Data?

Definisi: Penormalan pangkalan data ialah proses menyusun data dalam pangkalan data untuk mengurangkan lebihan data dan mengelakkan anomali data.

Objektif utama:

  • Mengurangkan lebihan data
  • Mengelakkan ketidakselarasan data
  • Mengelakkan anomali sisipan
  • Mengelakkan anomali kemas kini
  • Mengelakkan anomali pemadaman

Kebergantungan Fungsian (FD)

Kebergantungan fungsian bermaksud nilai satu atribut menentukan nilai atribut yang lain.

StudentID → StudentName

Maksudnya: dengan mengetahui StudentID, kita boleh menentukan StudentName. Simbol → bermaksud menentukan.

2. UNF — Bentuk Tidak Ternormal

UNF ialah struktur data yang belum dinormalisasi.

Ciri-ciri:

  • Mungkin mengandungi kumpulan berulang.
  • Mungkin mengandungi berbilang nilai dalam satu medan.
  • Data tidak tersusun dengan baik.
Contoh — Pendaftaran Kursus Pelajar (UNF)
StudentIDStudentNameCourses
S01AliBiology, Chemistry
S02MeiPhysics, Biology

Medan Courses mengandungi berbilang nilai kursus. Bagi S01, ia menyimpan kedua-dua Biology dan Chemistry. Ini adalah Kumpulan Berulang.

Masalah: Data tidak ternormal, menyukarkan pertanyaan, kemas kini, dan pengurusan setiap kursus secara berasingan.

3. 1NF — Bentuk Normal Pertama

Definisi: Jadual berada dalam 1NF jika semua atribut mengandungi nilai atom dan tiada kumpulan berulang.

Cara ia berfungsi:

  • Kenal pasti kumpulan berulang.
  • Pisahkan berbilang nilai.
  • Pastikan setiap sel mengandungi hanya satu nilai.
  • Kenal pasti kunci utama yang sesuai.
Contoh — 1NF (Pendaftaran Kursus Pelajar)
StudentIDStudentNameCourse
S01AliBiology
S01AliChemistry
S02MeiPhysics
S02MeiBiology

Sekarang setiap sel mempunyai satu nilai, jadi ia memenuhi 1NF. Walau bagaimanapun, StudentName masih berulang.

Ini membawa kita kepada 2NF.

4. Kunci Utama Komposit

Kunci Utama Komposit terdiri daripada dua atau lebih atribut yang digabungkan.

Contoh — Kunci Komposit (StudentID, CourseID)
StudentIDCourseIDStudentNameCourseNameMarks
S01C01AliBiology85
S01C02AliChemistry90
S02C01MeiBiology78

Andaikan: pelajar boleh mendaftar untuk berbilang kursus; kursus boleh mempunyai berbilang pelajar; Markah bergantung pada kedua-dua pelajar dan kursus.

(StudentID, CourseID) → Marks

StudentID dan CourseID bersama-sama menentukan Markah secara unik. Jadi Kunci Utama Komposit ialah (StudentID, CourseID).

5. Kebergantungan Fungsian Penuh

Definisi: Kebergantungan fungsian penuh berlaku apabila atribut bukan kunci bergantung pada keseluruhan kunci utama komposit, bukan sebahagian daripadanya.

Contoh:

(StudentID, CourseID) → Marks

Mengapa? StudentID sahaja tidak dapat menentukan Markah. CourseID sahaja juga tidak dapat menentukan Markah. Kedua-duanya diperlukan. Oleh itu, Markah adalah kebergantungan fungsian penuh.

Ingat: Penuh = bergantung pada KESELURUHAN kunci komposit.

6. Kebergantungan Fungsian Separa

Definisi: Kebergantungan fungsian separa berlaku apabila atribut bukan kunci bergantung hanya pada sebahagian kunci utama komposit dan bukan keseluruhan kunci.

Contoh:

StudentID → StudentName

Mengapa? Mengetahui StudentID sudah cukup untuk menentukan StudentName. Kita tidak memerlukan CourseID. Jadi StudentName bergantung pada sebahagian kunci komposit.

Contoh lain: CourseID → CourseName. CourseName hanya bergantung pada CourseID.

Cara menghapuskan? Pecahkan jadual:

JADUAL PELAJAR

StudentID (PK)StudentName
S01Ali
S02Mei

JADUAL KURSUS

CourseID (PK)CourseName
C01Biology
C02Chemistry

JADUAL PENDAFTARAN

StudentID (PK, FK)CourseID (PK, FK)Marks
S01C0185
S01C0290
S02C0178

Kini StudentName dan CourseName tidak lagi bergantung pada sebahagian kunci komposit. Ini menghapuskan Kebergantungan Fungsian Separa.

7. Kebergantungan Fungsian Transitif

Definisi: Kebergantungan fungsian transitif berlaku apabila atribut bukan kunci bergantung pada atribut bukan kunci lain dan bukannya bergantung secara langsung pada kunci utama.
Contoh — FD Transitif (Jabatan)
StudentID (PK)StudentNameDepartmentIDDepartmentName
S01AliD01Biology
S02MeiD02Chemistry
S03JohnD01Biology

Kita tahu: StudentID → DepartmentID dan DepartmentID → DepartmentName, oleh itu StudentID → DepartmentName.

Di sini DepartmentName tidak bergantung secara langsung pada StudentID; ia ditentukan melalui DepartmentID. Ini ialah Kebergantungan Fungsian Transitif.

Cara menghapuskan? Pecahkan jadual:

JADUAL PELAJAR

StudentID (PK)StudentNameDepartmentID (FK)
S01AliD01
S02MeiD02
S03JohnD01

JADUAL JABATAN

DepartmentID (PK)DepartmentName
D01Biology
D02Chemistry

Kini DepartmentName bergantung secara langsung pada DepartmentID, bukan secara tidak langsung melalui StudentID.

8. 2NF — Bentuk Normal Kedua

Definisi: Jadual berada dalam 2NF jika ia sudah berada dalam 1NF dan tiada kebergantungan fungsian separa.

Cara ia berfungsi:

  • Pastikan jadual berada dalam 1NF.
  • Kenal pasti kunci utama komposit.
  • Kenal pasti kebergantungan fungsian separa.
  • Hapuskan kebergantungan separa dengan memisahkan jadual.

Perkara penting: 2NF = 1NF + Tiada Kebergantungan Fungsian Separa.

Contoh — Hasil 2NF (pecahan sebelumnya)
StudentID (PK)StudentName
S01Ali
S02Mei
CourseID (PK)CourseName
C01Biology
C02Chemistry
StudentID (PK, FK)CourseID (PK, FK)Marks
S01C0185
S01C0290
S02C0178
Nota: Jika kunci utama terdiri daripada satu atribut, tiada kebergantungan separa yang disebabkan oleh kunci komposit.

9. 3NF — Bentuk Normal Ketiga

Definisi: Jadual berada dalam 3NF jika ia sudah berada dalam 2NF dan tiada kebergantungan fungsian transitif atribut bukan kunci pada kunci calon.

Cara ia berfungsi:

  • Pastikan jadual berada dalam 2NF.
  • Kenal pasti kebergantungan fungsian transitif.
  • Pisahkan atribut yang bergantung pada atribut bukan kunci lain.
  • Cipta jadual baharu dengan kunci utama dan kunci asing yang sesuai.

Perkara penting: 3NF = 2NF + Tiada Kebergantungan Fungsian Transitif.

Contoh — Hasil 3NF (pecahan jabatan)
StudentID (PK)StudentNameDepartmentID (FK)
S01AliD01
S02MeiD02
S03JohnD01
DepartmentID (PK)DepartmentName
D01Biology
D02Chemistry

Kini DepartmentName bergantung secara langsung pada DepartmentID, bukan secara tidak langsung melalui StudentID.

10. Ringkasan: UNF → 1NF → 2NF → 3NF

Bentuk NormalKeperluan UtamaMenghapuskan
UNFTidak ternormalKumpulan berulang belum diurus
1NFNilai AtomKumpulan Berulang
2NF1NF + Tiada FD SeparaKebergantungan Separa
3NF2NF + Tiada FD TransitifKebergantungan Transitif

Petua ingatan peperiksaan:

  • 1NF: Satu sel = Satu nilai
  • 2NF: Kebergantungan Kunci Penuh — hapuskan FD Separa
  • 3NF: Tiada apa-apa selain Kunci — hapuskan FD Transitif
Nota khas: Kedua-dua 2NF dan 3NF memerlukan pertimbangan Kunci Calon dan Kebergantungan Fungsian — bukan sekadar memeriksa data pendua.

Saya cadangkan: berlatih satu latihan penormalan penuh dari UNF langkah demi langkah ke 3NF, supaya anda benar-benar menguasai cara mengurai jadual dalam peperiksaan.

1. 什么是数据库规范化？

定义： 数据库规范化是将数据库中的数据进行有系统的整理，以减少重复数据，并避免数据异常。

主要目的：

  • 减少重复数据
  • 避免数据不一致
  • 避免插入异常
  • 避免更新异常
  • 避免删除异常

函数依赖 (Functional Dependency)

函数依赖指一个属性的值能够决定另一个属性的值。

StudentID → StudentName

意思是：只要知道 StudentID，就能确定对应的 StudentName。符号 → 代表 determines（决定）。

2. UNF — 未规范化

UNF 是尚未经过规范化的数据结构。

特点：

  • 可能存在重复组。
  • 一个字段可能包含多个值。
  • 数据尚未妥善整理。
例子 — 学生课程注册系统 (UNF)
StudentIDStudentNameCourses
S01AliBiology, Chemistry
S02MeiPhysics, Biology

这里的 Courses 字段包含多个课程值。例如 S01 的 Courses 同时储存 Biology 和 Chemistry。这就是一个 Repeating Group（重复组）。

问题： 数据不够规范，难以独立查询、更新和管理每个课程。

3. 1NF — 第一范式

定义： 当表格中的每一个字段都只包含一个原子值（Atomic Value），并且没有重复组时，就符合 1NF。

如何运作：

  • 找出重复组。
  • 分离多个值。
  • 确保每个单元格只有一个值。
  • 确定合适的主键。
例子 — 1NF (学生课程注册系统)
StudentIDStudentNameCourse
S01AliBiology
S01AliChemistry
S02MeiPhysics
S02MeiBiology

现在每个单元格只有一个值，因此符合 1NF。不过，你会发现 StudentName 仍然重复出现。

这就引出了 2NF。

4. 复合主键 (Composite Primary Key)

复合主键是由两个或以上的属性组合而成的主键。

例子 — 复合主键 (StudentID, CourseID)
StudentIDCourseIDStudentNameCourseNameMarks
S01C01AliBiology85
S01C02AliChemistry90
S02C01MeiBiology78

假设：一个学生可以注册多个课程；一个课程可以有多个学生；Marks 取决于学生和课程的组合。

(StudentID, CourseID) → Marks

StudentID 和 CourseID 必须组合起来，才能唯一确定一项成绩。所以复合主键是 (StudentID, CourseID)。

5. 完全函数依赖 (Full Functional Dependency)

定义： 完全函数依赖是指一个非主键属性必须依赖整个复合主键，而不是只依赖其中一部分。

例子：

(StudentID, CourseID) → Marks

为什么？StudentID 单独无法决定 Marks。CourseID 单独也无法决定 Marks。必须同时知道 StudentID 和 CourseID，才能确定 Marks。因此，Marks 属于完全函数依赖。

记忆： Full = Depends on the WHOLE composite key（依赖整个复合键）。

6. 部分函数依赖 (Partial Functional Dependency)

定义： 部分函数依赖是指非主键属性只依赖复合主键的其中一部分，而不是整个主键。

例子：

StudentID → StudentName

为什么？因为只要知道 StudentID，就能确定 StudentName。不需要知道 CourseID。因此，StudentName 只依赖复合主键的一部分。这就是部分函数依赖。

另一个例子：CourseID → CourseName。CourseName 只依赖 CourseID。

如何消除？ 将原本的表格拆分成不同的表格：

STUDENT TABLE

StudentID (PK)StudentName
S01Ali
S02Mei

COURSE TABLE

CourseID (PK)CourseName
C01Biology
C02Chemistry

REGISTRATION TABLE

StudentID (PK, FK)CourseID (PK, FK)Marks
S01C0185
S01C0290
S02C0178

现在 StudentName 和 CourseName 不再依赖复合主键的一部分而留在 Registration Table 中。这就是消除部分函数依赖。

7. 传递函数依赖 (Transitive Functional Dependency)

定义： 传递函数依赖是指一个非主键属性通过另一个非主键属性间接依赖主键。
例子 — 传递函数依赖 (部门)
StudentID (PK)StudentNameDepartmentIDDepartmentName
S01AliD01Biology
S02MeiD02Chemistry
S03JohnD01Biology

我们知道：StudentID → DepartmentID 以及 DepartmentID → DepartmentName，所以 StudentID → DepartmentName。

这里 DepartmentName 并不是直接依赖 StudentID，而是通过 DepartmentID 决定。这就是传递函数依赖。

如何消除？ 将表格拆分：

STUDENT TABLE

StudentID (PK)StudentNameDepartmentID (FK)
S01AliD01
S02MeiD02
S03JohnD01

DEPARTMENT TABLE

DepartmentID (PK)DepartmentName
D01Biology
D02Chemistry

现在 DepartmentName 直接依赖 DepartmentID，不再通过 StudentID 间接决定。

8. 2NF — 第二范式

定义： 一张表格必须先符合 1NF，并且不存在部分函数依赖，才能符合 2NF。

如何运作：

  • 确保表格符合 1NF。
  • 确定复合主键。
  • 找出部分函数依赖。
  • 通过拆分表格来消除部分依赖。

重点： 2NF = 1NF + 无部分函数依赖。

例子 — 2NF 结果 (之前的拆分)
StudentID (PK)StudentName
S01Ali
S02Mei
CourseID (PK)CourseName
C01Biology
C02Chemistry
StudentID (PK, FK)CourseID (PK, FK)Marks
S01C0185
S01C0290
S02C0178
注意：如果表格的主键只有一个属性，就不会存在由复合主键引起的部分函数依赖。

9. 3NF — 第三范式

定义： 一张表格必须先符合 2NF，并且不存在非主键属性对候选键的传递函数依赖，才能符合 3NF。

如何运作：

  • 确保表格符合 2NF。
  • 找出传递函数依赖。
  • 分离依赖其他非主键属性的属性。
  • 创建具有合适主键和外键的新表格。

重点： 3NF = 2NF + 无传递函数依赖。

例子 — 3NF 结果 (部门拆分)
StudentID (PK)StudentNameDepartmentID (FK)
S01AliD01
S02MeiD02
S03JohnD01
DepartmentID (PK)DepartmentName
D01Biology
D02Chemistry

现在 DepartmentName 直接依赖 DepartmentID，不再通过 StudentID 间接决定。

10. 总结：UNF → 1NF → 2NF → 3NF

范式主要要求消除什么？
UNF未规范化尚未处理重复组
1NF原子值重复组
2NF1NF + 无部分函数依赖部分依赖
3NF2NF + 无传递函数依赖传递依赖

考试记忆方式：

  • 1NF： 每个单元格只能有一个值
  • 2NF： 依赖整个主键 — 消除部分函数依赖
  • 3NF： 除主键外别无其他 — 消除传递函数依赖
特别注意：2NF 和 3NF 的判断都需要考虑候选键和函数依赖，不能只看表格有没有重复数据。

我的建议是下一步练习一道完整的规范化题目，从 UNF 一步一步转换到 3NF，这样你就能真正掌握如何在考试中拆分表格。
