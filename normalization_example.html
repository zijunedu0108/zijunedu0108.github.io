Normalization Process (UNF to 3NF)

Step-by-step transformation to eliminate redundancy and anomalies

UNF

Unnormalised Form

Why: This is the raw table. Book info and categories are crammed into a single cell.

StudentIDNameClassBookIDBookNameCategoryIDCategoryBorrowDateReturnDate

Goal

Eliminate Repeating Groups. In 1NF, every cell must contain only a single atomic value.

1NF

First Normal Form

Why: Separate comma-separated values into individual rows. Every cell now has one value.

Why the Underline (Primary Key)?

From what to what: Now that data is in single values, neither StudentID nor BookID alone can uniquely identify a row.

Composite Key: You need (StudentID, BookID) together to uniquely identify who borrowed which book. Thus, they are underlined as the Composite Primary Key.

Note: CategoryID is NOT a primary key here because knowing the category doesn't uniquely identify a borrowing record.

2NF

Second Normal Form

Why: Eliminate Partial Dependencies. In 1NF, Name & Class depend ONLY on StudentID. BookName, CategoryID, Category depend ONLY on BookID.

Transformation

From: One massive table with mixed dependencies.

To: Three clear tables. Attributes follow their respective primary keys (StudentID or BookID), leaving only the truly combined data (dates) in the BORROWING table.

3NF

Third Normal Form

Why: Eliminate Transitive Dependency. In the 2NF BOOK table, BookID → CategoryID → Category. Category is not directly dependent on BookID, but indirectly via CategoryID.

NEW: CATEGORY Table

CategoryIDCategory
C01Programming
C02Database
C03Networking
C04Multimedia

BookIDBookNameCategoryID (FK)

B002Computer NetworksC03
B003SQLC02
B004Media DesignC04

Transformation

From: A 2NF BOOK table with redundant text values (e.g., "Programming" repeated for every book).

To: A dedicated CATEGORY table where CategoryID is the Primary Key. In the BOOK table, CategoryID becomes a Foreign Key referencing the category. This eliminates redundancy and update anomalies.

Mengapa Garis Bawah (Kunci Utama)?

Dari apa ke apa: Memandangkan data kini dalam nilai tunggal, StudentID atau BookID sahaja tidak dapat mengenal pasti baris secara unik.

Kunci Komposit: Anda memerlukan (StudentID, BookID) bersama-sama untuk mengenal pasti siapa meminjam buku mana. Oleh itu, ia digariskan sebagai Kunci Utama Komposit.

Nota: CategoryID BUKAN kunci utama di sini kerana mengetahui kategori tidak mengenal pasti rekod pinjaman secara unik.

2NF

Bentuk Normal Kedua

Mengapa: Hapuskan Kebergantungan Separa. Dalam 1NF, Name & Class hanya bergantung pada StudentID. BookName, CategoryID, Category hanya bergantung pada BookID.

Transformasi

Dari: Satu jadual besar dengan kebergantungan bercampur.

Ke: Tiga jadual yang jelas. Atribut mengikut kunci utama masing-masing (StudentID atau BookID), meninggalkan hanya data yang benar-benar digabungkan (tarikh) dalam jadual BORROWING.

Bentuk Normal Ketiga

Mengapa: Hapuskan Kebergantungan Transitif. Dalam jadual BOOK 2NF, BookID → CategoryID → Category. Category tidak bergantung secara langsung pada BookID, tetapi secara tidak langsung melalui CategoryID.

Dari: Jadual BOOK 2NF dengan nilai teks berlebihan (contohnya, "Programming" diulang untuk setiap buku).

Ke: Jadual CATEGORY khusus di mana CategoryID ialah Kunci Utama. Dalam jadual BOOK, CategoryID menjadi Kunci Asing yang merujuk kepada kategori. Ini menghapuskan lebihan dan anomali kemas kini.

数据库规范化过程 (UNF 到 3NF)

一步步消除数据冗余和异常的演变过程

UNF

未规范化形式

为什么：这是最原始的表格。为了省事，图书信息和分类信息被塞进了同一个单元格。

StudentIDNameClassBookIDBookNameCategoryIDCategoryBorrowDateReturnDate
S001Aina6A B001, B003 Python, SQL C01, C02 Programming, Database 10/06/202617/06/2026
S002Amir6B B002Computer NetworksC03Networking11/06/202618/06/2026
S003Siti6A B004, B005 Media Design, HTML C04, C01 Multimedia, Programming 12/06/202619/06/2026

目标

消除重复组 (Repeating Groups)。在 1NF 中，每个单元格只能包含一个原子值。

1NF

第一范式

为什么这样改：把用逗号隔开的数据拆成多行。现在每个格子只有一个值。

StudentID BookID NameClassBookNameCategoryIDCategoryBorrowDateReturnDate
S001B001Aina6APythonC01Programming10/06/202617/06/2026
S001B003Aina6ASQLC02Database10/06/202617/06/2026
S002B002Amir6BComputer NetworksC03Networking11/06/202618/06/2026
S003B004Siti6AMedia DesignC04Multimedia12/06/202619/06/2026
S003B005Siti6AHTML CodeC01Programming12/06/202619/06/2026

为什么画下划线 (主键)？

从什么得到什么：因为数据拆成了单值，单靠 StudentID（比如 S001 有两行）或单靠 BookID 无法唯一确定一行。

必须组合起来：必须同时知道 (StudentID, BookID) 才能唯一确定谁借了哪本书。所以形成了复合主键，并画上下划线。

注意：此时 CategoryID 只是一般属性，不能做主键，因为知道了分类 C01，并不代表唯一知道是谁借了哪本书。

2NF

第二范式

为什么这样改：消除部分函数依赖 (Partial Dependencies)。在 1NF 表中，Name 和 Class 只依赖 StudentID；BookName、CategoryID 等只依赖 BookID。

从什么得到什么 (Transformation)

从：一张包含所有信息、依赖关系混乱的超大表。

得到：三张逻辑清晰的表。属性跟着各自的主键走（StudentID 或 BookID），只有真正依赖于两者的 BorrowDate 和 ReturnDate 留在借阅表里。

3NF

第三范式

为什么这样改：消除传递函数依赖 (Transitive Dependency)。在 2NF 的 BOOK 表中，BookID → CategoryID → Category。Category 不是直接依赖 BookID，而是通过 CategoryID 间接决定的。

从什么得到什么 (Transformation)

从：2NF 的 BOOK 表中包含冗余的 Category 文本（每次出现 C01 都要重复写一遍 Programming）。

得到：独立出 CATEGORY 表。在 CATEGORY 表里，CategoryID 成为唯一的主键。在 BOOK 表里，CategoryID 变成了外键 (Foreign Key)。这不仅省空间，还解决了更新异常。
